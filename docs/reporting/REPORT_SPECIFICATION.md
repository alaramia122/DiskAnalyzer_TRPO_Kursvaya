# Спецификация финального отчёта

## 1. Данные титульного листа

Использовать следующий текст и порядок, адаптируя оформление к образцу кафедры:

- Министерство науки и высшего образования Российской Федерации
Титульный лист воспроизводится по образцу «Осипенко_ГВ_Отчет_курсовая_ПЯВУ (1).docx». Сохранять порядок, формулировки и поля образца. Допустимые изменения только следующие:
- заменить слово «БЮДЖЕТНОЕ» на «АВТОНОМНОЕ» в наименовании учреждения;
- заменить название дисциплины на «Технологии разработки программного обеспечения»;
- указать год 2026.

Остальной текст и порядок титульного листа оставить как в образце, включая поля студента, преподавателя и даты сдачи.

## 2. Обязательная структура

1. Титульный лист.
2. Оглавление с разделами и подразделами, сформированное из фактических заголовков отчёта.
3. Задание.
4. Псевдокод алгоритмов решения задачи:
   - основной алгоритм работы программы;
   - организация дерева каталогов (не называть его префиксным деревом, если это не подтверждается реализацией);
   - алгоритм сканирования файловой системы;
   - алгоритм классификации файла;
   - алгоритм агрегации статистики;
   - алгоритм подготовки данных визуализации;
   - алгоритм навигации и обновления содержимого;
   - алгоритм экспорта;
   - другие алгоритмы, только если они есть в актуальном коде.
5. Сведения о программной реализации:
   - язык программирования и фреймворки;
   - входные и выходные данные;
   - спроектированные структуры и программные единицы;
   - архитектура, связи компонентов и потоки данных;
   - инструкция пользователя.
6. Листинг:
   - полный текст релевантных файлов .h и .cpp из src/ и tests/;
   - CMakeLists.txt;
   - workflow сборки и тестирования, если присутствует;
   - исключить бинарные файлы, build-каталоги, кэш и сгенерированные файлы;
   - перед каждым листингом указать путь относительно корня репозитория.
7. Тестирование:
   - реальные автоматические тесты;
   - таблица сценариев с колонками «Вводимое значение», «Предполагаемая реакция», «Действительная реакция»;
   - ручные проверки перечислить по проверявшимся функциям и указать итоговый результат; не описывать хронологию повторных раундов и исправлений;
   - статус автоматической сборки и CTest указать по фактическому GitHub Actions run, содержащему commit, из которого сгенерирован отчёт.
8. Заключение и известные ограничения.

## 3. Правила точности

- Исходный код текущего checkout — первичный источник фактов о реализации.
- ARCHITECTURE.md, TESTING.md, USER_GUIDE.md и FINAL_REPORT.md — вспомогательные источники. При расхождении сверить код и явно разрешить противоречие.
- Не придумывать функции, классы, поля, enum-значения, форматы экспорта, кнопки интерфейса или результаты тестов.
- Извлечь реальные определения типов, публичные методы и сигнатуры; описание программных единиц должно соответствовать им.
- Не утверждать, что все GUI-сценарии проверены автоматическими тестами, если CTest их не покрывает.
- Smoke-test, подтверждающий, что GUI-процесс не завершился до таймаута, не доказывает корректность всех элементов интерфейса.
- Ручные сценарии без фактического прогона помечать «не выполнялся в рамках автоматической проверки / требуется ручная приёмка», а не «пройден».
- Для CI указывать конкретный run/commit и статус только после проверки GitHub Actions; workflow генерации отчёта обязан выполнить CMake build и CTest для того же commit и передать подтверждённый результат генератору.
- Контрольные размеры синтетического набора не выдавать за результат измерения.
- Избегать слишком широких колонок; длинные сигнатуры переносить или выделять в листинг.
- Листинги оформлять моноширинным шрифтом; не терять строки, не обрезать содержимое и не пропускать файлы молча.
- Автоматически проверять, что число исходных файлов в листинге совпадает с числом найденных релевантных файлов.
- После генерации проверить DOCX: контейнер открывается, обязательные разделы присутствуют, листинги непустые.

## 4. Требования к таблицам

### Программные единицы

Разделить описание на отдельные группы по видам программных единиц: классы и структуры; перечисления и псевдонимы типов; интерфейсы; функции и методы. Если отдельный вид в проекте отсутствует, это следует отметить.

Для каждой программной единицы привести:
- имя и точную сигнатуру (для типа — объявление и состав, для функции/метода — возвращаемый тип, параметры и квалификаторы);
- назначение и причину существования в архитектуре;
- каждый аргумент с ролью, описанием и способом передачи (значение, указатель, ссылка, const-ссылка, rvalue-ссылка; входной, выходной или входо-выходной параметр);
- выходные данные: возвращаемый тип и смысл результата либо явное указание, что значение не возвращается;
- изменения состояния объекта, переданных данных и внешних ресурсов (файловая система, файлы экспорта, UI-сигналы/уведомления). Если эффект нельзя достоверно установить по сигнатуре, изучить тело реализации; не выводить эффект только из имени.
- файл-источник.

Включить все пользовательские типы и все функции/методы, входящие в объём исходного кода, а не только центральные классы. Для перечислений перечислить значения. Не создавать фиктивную таблицу глобальных переменных: если глобальных пользовательских переменных нет, указать это прямо. Автоматически извлечённые описания должны быть сверены с исходниками; не выдавать эвристику по имени за подтверждённую семантику.

### Входные и выходные данные

Описать реальные входы: путь каталога, команды UI, доступность файловой системы, содержимое файловой системы. Описать выходы, подтверждённые кодом: дерево каталогов, агрегированные размеры/количества, таблицы/диаграмма, экспорт JSON/TXT, статусы и ошибки.

### Тестирование

Для каждого сценария указать действие или ввод, ожидаемую реакцию, фактическую реакцию только на основании результата теста или проверяемого запуска и источник подтверждения (имя теста, CTest/CI run или «ручной тест не выполнялся»).

## 5. Критерии готовности

- DOCX создан, а ссылка на файл действительно существует.
- DOCX открывается и проходит программную проверку структуры.
- Все обязательные разделы присутствуют.
- Листинги включают все файлы заданного перечня.
- Описание программных единиц сопоставлено с актуальным кодом.
- Результаты тестов не выдуманы.
- Документ визуально проверен на плохие разрывы страниц, обрезанный код, пустые таблицы и лишние страницы.
- Итоговое сообщение перечисляет артефакты, commit/PR и непроверенные пункты.
