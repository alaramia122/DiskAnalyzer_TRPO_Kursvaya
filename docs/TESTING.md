# Проверки и тестирование Disk Analyzer

Документ описывает автоматические проверки, ручные сценарии и критерии приёмки. Успешная автоматическая сборка не заменяет ручную проверку пользовательского интерфейса и переносимых пакетов на целевых ОС.

## 1. Автоматические проверки

Сборка и тесты запускаются командами:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Единый workflow **Build, test and package** содержит независимые jobs для Windows x64 и Linux x86_64. Оба конфигурируют проект, собирают Release-конфигурацию и запускают CTest. Windows job формирует ZIP с развёрнутыми Qt runtime-библиотеками и проверяет запуск приложения. Linux job собирает AppImage с упакованными Qt-библиотеками и плагинами и выполняет smoke-test запуска через виртуальный X11-дисплей. При создании релиза workflow публикует оба пакета только после успешного завершения обоих jobs.

Автоматический набор включает:
- интеграционные проверки обхода тестового дерева, direct/subtree-статистики и классификации по расширению;
- пустые каталоги и символические ссылки при доступности соответствующей функции в окружении;
- повторную агрегацию без двойного учёта;
- отмену анализа и ошибочный корневой путь;
- экспорт JSON/TXT и обработку ошибочных путей;
- жизненный цикл ApplicationController, отмену и повторный запуск;
- преобразование статистики для Direct/Subtree/Total;
- кэширование и чтение непосредственного содержимого каталогов.

## 2. Ручная проверка переносимых пакетов

Для каждой платформы отдельно:

1. Скачать пакет из GitHub Releases. Пока релиз не опубликован, временный артефакт можно скачать из успешного запуска workflow в GitHub Actions.
2. Распаковать его (для AppImage распаковка не обязательна).
3. Проверить наличие исполняемого файла и инструкции запуска.
4. Запустить приложение вне IDE.
5. Выполнить анализ контрольного каталога с заранее известными размерами и расширениями.
6. Проверить Direct, Subtree и Total, категории, проценты и диаграмму.
7. Проверить навигацию, обновление списка содержимого, отмену и отзывчивость интерфейса.
8. Экспортировать результат в JSON и TXT и сопоставить его с интерфейсом.
9. Проверить поведение при недоступном корневом пути и ошибках доступа к вложенным каталогам.

Для Windows нужно подтвердить запуск ZIP-пакета без отдельной установки Qt. Для Linux нужно проверить AppImage на целевом дистрибутиве. CI smoke-test подтверждает запуск приложения в среде сборки; он не доказывает совместимость со всеми версиями Windows или дистрибутивами Linux.

## 3. Контрольный набор

Контрольное дерево должно содержать:

```text
TestData/
├── Documents/
│   ├── report.txt    (100 байт)
│   └── notes.txt     (200 байт)
├── Images/
│   └── picture.png   (300 байт)
├── Archive/
│   └── backup.zip    (400 байт)
└── readme.md         (500 байт)
```

Ожидаемые значения:
- количество файлов — 5;
- общий размер — 1500 байт;
- Documents — 300 байт;
- Images — 300 байт;
- Archive — 400 байт;
- файлы непосредственно в корне TestData — 500 байт.

В протоколе необходимо фиксировать реальные размеры, возвращаемые файловой системой: при создании контрольных файлов следует убедиться, что их размеры в байтах действительно равны указанным значениям.

## 4. Результаты и доказательства

Не записывайте сценарий как успешно пройденный, если для него нет фактического результата. Для каждой приёмки фиксируйте:
- SHA коммита и ссылку на запуск GitHub Actions;
- версию ОС и конфигурацию среды;
- результат CTest и smoke-test пакета;
- ожидаемые и фактические значения контрольного набора;
- запуск GUI вне IDE;
- результаты проверки экспорта JSON/TXT;
- скриншоты главного окна, статистики и диаграммы;
- ошибки доступа, неполные результаты и другие ограничения.

Сведения о ранее выполненных ручных проверках должны относиться к конкретной версии исходного кода. Если нет проверяемого протокола, эти сведения следует считать неподтверждёнными и провести проверку повторно.

## 5. Критерии приёмки

Проверка считается успешной для конкретного сценария, если фактическое поведение соответствует ожидаемому результату и это подтверждено записью в протоколе. Успешная автоматическая сборка сама по себе не подтверждает все сценарии ручной приёмки. Ошибки доступа к части дерева должны отражаться как ограничения полноты анализа, а не скрываться или трактоваться как отсутствие файлов.
