# Проверки и тестирование Disk Analyzer

Документ описывает автоматические проверки, ручные сценарии и фактически зафиксированные результаты. Он не заменяет официальный протокол испытаний или пояснительную записку к курсовой работе.

## 1. Автоматические проверки

Сборка и тесты запускаются командами:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

GitHub Actions содержит отдельные workflow для Windows x64 и Linux x86_64. Оба должны конфигурировать проект, собирать Release-конфигурацию и запускать CTest. Linux workflow использует Ubuntu 22.04 и системные Qt 5 development packages. Успешный CI подтверждает прохождение тестов только в соответствующей среде и не заменяет ручную проверку графического интерфейса на целевых системах.

Автоматический набор включает:
- интеграционные проверки обхода тестового дерева, direct/subtree-статистики и классификации по расширению;
- пустые каталоги и символические ссылки при доступности соответствующей функции в окружении;
- повторную агрегацию без двойного учёта;
- отмену анализа и ошибочный корневой путь;
- экспорт JSON/TXT и обработку ошибочных путей;
- жизненный цикл ApplicationController, отмену и повторный запуск;
- преобразование статистики для Direct/Subtree/Total;
- кэширование и чтение непосредственного содержимого каталогов.

## 2. Ручная проверка переносимых пакетов

Для каждой платформы отдельно:

1. Скачать архив из GitHub Actions или GitHub Releases.
2. Распаковать его в новый каталог.
3. Проверить наличие исполняемого файла и инструкции запуска.
4. Запустить приложение вне IDE.
5. Выполнить анализ контрольного каталога с заранее известными размерами и расширениями.
6. Проверить Direct, Subtree и Total, категории, проценты и диаграмму.
7. Проверить навигацию, обновление списка содержимого, отмену и отзывчивость интерфейса.
8. Экспортировать результат в JSON и TXT и сопоставить его с интерфейсом.
9. Проверить поведение при недоступном корневом пути и ошибках доступа к вложенным каталогам.

Для Windows нужно подтвердить запуск ZIP-пакета без отдельной установки Qt. Для Linux необходимо зафиксировать дистрибутив, версию ОС и наличие Qt 5 runtime-библиотек. Текущий Linux TAR.GZ содержит исполняемый файл, но не упаковывает системные Qt-библиотеки, поэтому он не является полностью автономным пакетом.

## 3. Контрольный набор

Используемый в ручном протоколе набор TestData:

```text
TestData/
├── Documents/
│   ├── report.txt    (100 байт)
│   └── notes.txt     (200 байт)
├── Images/
│   └── picture.png   (300 байт)
├── Archive/
│   └── backup.zip    (400 байт)
└── readme.md         (500 байт)
```

Ожидаемые значения:
- количество файлов — 5;
- общий размер — 1500 байт;
- Documents — 300 байт;
- Images — 300 байт;
- Archive — 400 байт;
- файлы непосредственно в корне TestData — 500 байт.

## 4. Зафиксированные результаты ручных испытаний

По предоставленному протоколу ручного тестирования:

- переносимая сборка Windows запускалась из распакованного архива без необходимости запуска компилятора или ручной установки Qt;
- на контрольном наборе из пяти файлов суммарным размером 1500 байт проверялись размеры и статистика каталогов;
- проверялись пустые каталоги, вложенные каталоги, неизвестные расширения, Direct/Subtree-статистика, категории и диаграмма;
- навигация по результатам на большой файловой системе не запускала полное повторное сканирование;
- проверялись экспорт JSON и TXT, отзывчивость интерфейса, прогресс, отмена, закрытие приложения и повторный запуск;
- при анализе всего системного диска встречались отказы в доступе к некоторым системным каталогам. Такие данные нельзя считать полностью проанализированными.

В протоколе также отмечались проблемы отображения размеров подкаталогов и наложения подписей диаграммы. В последующей версии сообщалось об исправлении отображения размеров поддеревьев и категорий, а также о переносе точных значений диаграммы во всплывающие подсказки. Эти изменения следует связывать с соответствующей версией исходного кода, а не трактовать как доказательство отсутствия любых возможных дефектов интерфейса.

Протокол содержит отдельные сценарии, результаты которых отмечены как приблизительные или требующие дополнительной проверки. Их нельзя автоматически считать успешно пройденными без дополнительного подтверждения. Linux-сборка на момент составления документа ещё должна пройти реальный запуск и ручную проверку на целевой системе.

## 5. Фиксация новых результатов

Для повторной приёмки рекомендуется записывать:
- SHA коммита и ссылку на запуск GitHub Actions;
- версию ОС, компилятора и Qt;
- конфигурацию сборки и итог CTest;
- состав контрольного набора и ожидаемые/фактические значения;
- результаты запуска переносимого пакета без IDE;
- результаты проверки JSON/TXT;
- скриншоты главного окна, статистики и диаграммы;
- ошибки доступа, неполные результаты и другие обнаруженные ограничения.

## 6. Критерии приёмки

Проверка считается успешной для конкретного сценария, если фактическое поведение соответствует ожидаемому результату и это подтверждено записью в протоколе. Успешная автоматическая сборка сама по себе не подтверждает все сценарии ручной приёмки. Ошибки доступа к части дерева должны отражаться как ограничения полноты анализа, а не скрываться или трактоваться как отсутствие файлов.
